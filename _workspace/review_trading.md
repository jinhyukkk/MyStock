## 3. 돈이 새는 지점 (Money Leak)

### ML-1. 최상위 등급이 3년간 0회 발생 — 5등급 UI가 실제로는 3등급 (치명)

**증상** `강력매수`/`강력매도` 등급이 구조적으로 도달 불가능.
**근거** `backend/app/scoring.py:9-14`(임계값 ±60), `scoring.py:3-4`(가중치), `scoring.py:143`(가중합).
스윙 점수의 이론적 최대치 = 0.20·80 + 0.20·80 + 0.20·80 + 0.15·60 + 0.15·70 + 0.10·50 = **72.5**.
60점을 넘으려면 `RSI<30`(과매도)과 `MACD 골든크로스`+`20/60일 골든크로스`(상승 전환)가 **동시에** 성립해야 하는데 이 둘은 서로 배타적이다. 게다가 `scoring.py:112-124`의 국면 반감이 극단값을 추가로 깎는다.

**실측** DB의 15종목 × 약 966 신호일 = **13,828 표본**에서:

| 등급 | 발생 수 | 비중 |
|---|---|---|
| 강력매수 | **0** | 0.0% |
| 매수 | 573 | 4.1% |
| 중립 | 12,697 | 91.8% |
| 매도 | 558 | 4.0% |
| 강력매도 | **0** | 0.0% |

**손실 시나리오** 사용자는 "매수"를 중간 등급으로 해석해 사이즈를 절반만 넣는다. 실제로는 그것이 이 시스템이 낼 수 있는 최고 신호다. 반대로 백테스트 표에 강력매수 행이 비어 있는 것을 "데이터가 아직 안 쌓였다"로 오해하고 언젠가 나올 최상위 신호를 기다린다 — 영원히 오지 않는다. 등급이 사이징의 입력인 시스템에서 최상위 등급이 죽은 코드면 사이징 규칙 전체가 죽는다.
**수정 방향** 임계값을 실측 점수 분위수(예: 상위 5%/20%)로 재보정하거나 `±60 → ±40/±15`로 하향. 최소한 백테스트 결과에 "이 등급은 관측 기간 중 0회"를 명시.

### ML-2. 실현손익에 수수료·세금이 존재하지 않는다 (치명)

**증상** 원장·승률·손익비가 전부 gross.
**근거** `backend/app/portfolio.py:27-28`
```python
"pnl": round((t["price"] - h["avg_price"]) * qty, 4),
"pnl_pct": round((t["price"] / h["avg_price"] - 1) * 100, 2),
```
`schema.sql:10-20`의 trades 테이블에 fee·tax 컬럼 자체가 없다. `portfolio.py:57-58`의 승패 판정(`pnl > 0`)과 `portfolio.py:61`의 손익비도 같은 gross 값을 쓴다. 프론트(`frontend/src/pages/Portfolio.tsx:206-235`)는 이를 "총 실현손익 / 승률 / 손익비"로 아무 단서 없이 표기.

**손실 시나리오** 한국 주식 왕복 비용은 증권거래세 + 위탁수수료 + 스프레드로 대략 0.3%p 수준이다(백테스트는 이를 `backtest.py:13`에서 인정하면서 원장에서는 무시). 평균 보유 5일, 월 4회전, 원금 1억이면 연 48회전 × 0.3% ≈ **연 1,440만 원**이 원장에서 사라진다. "승률 58%, 손익비 1.4"로 보이는 계좌가 net으로는 마이너스일 수 있고, 사용자는 통계가 좋으니 회전을 더 늘린다 — 정확히 반대로 가야 할 방향.
**수정 방향** trades에 `fee`, `tax` 컬럼 추가 → `_walk_trades`에서 매수 수수료를 평단에 가산, 매도 수수료·세금을 pnl에서 차감. 승률/손익비를 net 기준으로 재계산. 과거 행은 시장별 기본 요율로 추정하되 "추정" 배지.

### ML-3. 환율 부분 정산 — 미국 주식 실현손익이 최대 40%대 어긋난다

**증상** 손익 전액을 **매도 시점** 환율로만 환산. 원금에 붙은 환차손익이 통째로 누락.
**근거** `backend/app/portfolio.py:29-30`(주석이 한계를 인정), `portfolio.py:55` `rate = r.get("fx_rate") or ...`, `portfolio.py:56` `total_krw += r["pnl"] * rate`.

**손실 시나리오** AAPL 100주를 $200(USDKRW 1,300)에 사서 $220(USDKRW 1,400)에 매도.
- 실제 원화 손익 = 220×100×1400 − 200×100×1300 = 30,800,000 − 26,000,000 = **₩4,800,000**
- 앱 표기 = (220−200)×100×1400 = **₩2,800,000**
- 오차 **−₩2,000,000 (41.7% 과소)**

반대로 원화 강세 구간에서는 실제 원화 손실을 과소 표기해 "달러 자산은 잘 버텼다"는 착시를 만든다. 이 숫자로 KR/US 배분을 결정하면 배분 자체가 잘못된 근거 위에 선다.
**수정 방향** `_walk_trades`가 평단과 함께 **평균 매수 환율**을 이동평균으로 추적하고, 실현손익을 `매도가×수량×매도환율 − 평단×수량×평균매수환율`로 계산. 손익을 가격 손익 / 환 손익으로 분리 표기하면 복기가 훨씬 정확해진다.

### ML-4. 포지션 사이징에 상한이 없다 — 계좌 100% 초과를 제안할 수 있다

**증상** 저변동성 종목일수록 제안 수량이 무한 증가.
**근거** `backend/app/service.py:266-275`
```python
risk_krw = total * 0.01
"position_size_1pct": round(risk_krw / (2 * atr * fx), 4) if total > 0 else None,
```
제안 노셔널 = `total × 0.01 × price / (2×ATR)`. 즉 **2×ATR이 주가의 1%면 노셔널 = 총자산 전액**, 0.6%면 **총자산의 167%**(레버리지).
프론트(`frontend/src/pages/TickerDetail.tsx:180-188`)는 이 수량을 "계좌 1% 리스크 수량"으로 경고 없이 표시하고, 안내 문구는 "총자산의 1%만 잃는 수량"이라고 안심시킨다.

**손실 시나리오** 총자산 1억, ATR이 주가의 0.5%인 채권/배당 ETF(단기 ATR 축소 구간의 대형주도 자주 이 영역에 들어간다). 2×ATR = 1% → 제안 수량의 평가액 = **1억 = 계좌 전액 단일 종목**. 이 종목이 하루 −8% 갭(ATR 대비 16σ급이지만 실제로 일어난다: 실적 쇼크·정책 이벤트)을 맞으면 계획 손실 1%가 아니라 **−800만 원(계좌의 8%)**.
추가로 계좌 총 리스크 합산이 없다. 5종목에 각각 이 수량을 적용하면 "총 리스크 5%"라고 믿게 되지만, `portfolio.py:150-157`이 계산하는 상관계수가 0.8이면 실질 동시 리스크는 5%가 아니라 4%대 단일 베팅에 가깝다.
**수정 방향** (a) 노셔널 캡 — `min(risk_krw/(2·ATR·fx), total×MAX_WEIGHT/price)`, MAX_WEIGHT 기본 20%. (b) 기존 보유 수량을 차감한 **추가 매수 가능 수량**으로 제시. (c) 계좌 전체 미결 리스크 합계(모든 보유 × 2ATR)를 표시하고 상한(예: 6%) 초과 시 경고.

### ML-5. 손절 알림이 일봉 종가 + 시간당 갱신 — 계획 손실의 2~3배로 나간다

**증상** 앱이 2×ATR 손절을 제안하지만, 그 손절을 감시하는 장치는 하루 한 번 갱신되는 종가다.
**근거** `backend/app/service.py:121-124`(`close <= r["value"]`), 이 `close`의 출처는 `service.py:57-58` → `_latest_close_and_change` → `db.load_prices(..., limit=2)` 즉 **저장된 일봉 종가**. 갱신 주기는 `backend/app/main.py:14` `REFRESH_INTERVAL = 60*60`.

**손실 시나리오** ATR이 주가의 2%인 종목 → 제안 손절 −4%. 장중 −9%까지 밀렸다가 −3%로 마감하면 **알림 0건**(종가가 손절선 위). 반대로 −6%로 마감하면 알림은 오지만 이미 장이 끝났고, 다음 날 −3% 갭 하락 시가에 체결 → 실제 손실 **−9%**. 사이징이 가정한 "총자산 1%"는 실제로 **2.25%**가 된다. 3번 연속이면 계획 3%가 6.75%.
게다가 텔레그램 발송은 `service.py:63`에서 **전체 갱신(symbol=None)** 경로에서만 호출되고, 룰당 하루 1회로 제한(`service.py:146-148`)돼 재진입 감시가 안 된다.
**수정 방향** (a) 최소한 UI/알림에 "이 손절가는 자동 예약주문이 아니며 종가 기준으로만 감시된다"를 명시. (b) 일중 저가(`low`)로 터치 여부를 판정해 사후에라도 "장중 손절선 이탈" 표기. (c) 갭 리스크를 사이징에 반영 — 손절 폭에 갭 버퍼(예: ×1.3)를 곱한 보수적 수량을 함께 제시.

### ML-6. 백테스트 승률이 비용 차감 전 기준 (표시 왜곡)

**증상** 평균 수익률만 −0.3%p 하고, 승률은 gross 그대로.
**근거** `backend/app/backtest.py:59-60`
```python
entry[f"avg_net{h}"] = round(entry[f"avg_fwd{h}"] - COST_PCT, 2) if vals else None
entry[f"win{h}"]     = round(sum(v > 0 for v in vals) / len(vals) * 100, 1) if vals else None
```
`v > 0`이지 `v > COST_PCT`가 아니다. 프론트(`frontend/src/pages/TickerDetail.tsx:210, 215`)는 이 승률을 "순" 표기 옆에 나란히 놓아 같은 기준처럼 보이게 한다.

**손실 시나리오** 5일 horizon은 기대수익 자체가 작아 0~0.3% 구간에 표본이 두껍게 몰린다. 이 구간이 전부 승 → 패로 뒤집히면 승률이 수 %p 단위로 내려간다. 사용자는 "승률 60%짜리 신호"를 믿고 켈리 감각으로 사이즈를 키우지만 실제 net 승률은 그보다 낮다.
**수정 방향** `win{h}`를 `v > COST_PCT` 기준으로 계산하거나, gross/net 두 승률을 모두 표기.

### ML-7. 표본 중첩 — 표기 표본 수가 실제보다 2.8배 부풀려져 있다

**증상** 인접일 신호를 독립 표본으로 집계.
**근거** `backend/app/backtest.py:32` 루프가 **매 거래일**마다 표본을 만들고, `backtest.py:58`이 단순 산술평균. 20일 forward 수익률은 최대 19일이 겹친다.
신호가 여러 날 이어지는 구조적 원인도 있다 — `scoring.py:29-30`의 MACD 크로스는 `hist.tail(4)`로 **최대 4일간** 같은 크로스를 재보고하고, `scoring.py:40`의 이평 크로스는 `iloc[-1]` vs `iloc[-6]` 비교라 **5일간** 같은 골든크로스를 반복 신고한다.

**실측** DB 15종목 매수 등급 20일 구간:
- 신호일(표본) **569**개 → 20일 비중첩 에피소드 **202**개
- 평균 fwd20 **+3.99%**, 중앙값 +2.54%, 승률 61.5%
- 표준오차: 순진한 n=569 기준 **±0.59%p** → 중첩 보정(에피소드 202) **±1.00%p**

**손실 시나리오** 프론트는 `표본 {backtest.samples}일`(TickerDetail.tsx:194)로 종목당 900+ 표본을 광고한다. 종목 단위로 내려가면 AAPL 매수 47일 = 에피소드 약 13개다. 이 13개 표본으로 만든 "+5.2%" 숫자를 통계적 우위로 착각해 사이즈를 키우는 것이 전형적인 파산 경로다. 주의 문구(`TickerDetail.tsx:196`)는 있지만 **숫자 자체는 보정되지 않았고** 문구는 12px 회색이다.
**수정 방향** 비중첩 에피소드 수를 `n`과 함께 표기하고, 평균 옆에 **±1σ 신뢰구간**을 붙인다(중첩 보정 표준오차 사용). 등급별 에피소드 30개 미만이면 수치를 숨기거나 회색 처리.

### ML-8. 검증한 전략과 권장하는 전략이 다르다

**증상** 백테스트는 "손절 없이 5/20일 무조건 보유", 앱 권장은 "2×ATR 손절".
**근거** `backtest.py:42` `fwd = (closes.iloc[i + h] / closes.iloc[i] - 1) * 100` — 중간 경로 무시, 청산 규칙 없음. 반면 `service.py:268` `stop = close - 2 * atr`, UI는 "진입 전 손절가를 먼저 정하세요"(TickerDetail.tsx:188).
**손실 시나리오** 평균 +3.99%(20일)의 경로 중 상당수는 도중에 −2×ATR을 찍고 회복한 것이다. 실제로 손절을 걸면 그 표본들은 −4%로 확정되고 반등분은 못 받는다. 즉 사용자가 앱 지시대로 손절을 걸면 **백테스트가 약속한 수익률을 구조적으로 받을 수 없다**. 반대로 백테스트 숫자를 믿고 손절을 안 걸면 사이징 전제(1% 리스크)가 무너진다. 어느 쪽이든 진다.
**수정 방향** 백테스트에 청산 규칙을 이식 — 매 봉의 `low`가 진입가−2ATR을 터치하면 그 가격에 청산, 아니면 h일 종가 청산. 그러면 표시 수익률이 실제로 실행 가능한 숫자가 된다.

### ML-9. 체결 가정: 신호를 만든 종가에 체결한다고 가정 + 장중 부분 봉 리페인팅

**증상** 실행 불가능한 체결 가격으로 성과를 계산하고, 실시간 등급은 미확정 봉으로 계산된다.
**근거** `backtest.py:42`에서 진입가 = `closes.iloc[i]` — 그 날 종가로 계산한 RSI/MACD/볼린저를 보고 **그 날 종가에** 사는 셈.
실전 경로: `fetchers.py:35`(KR, `fdr.DataReader(symbol, start)`)와 `fetchers.py:40`(US, `yf.Ticker(...).history(...)`)는 **장중에도 당일 미완성 봉을 반환**한다. `service.py:70-79`가 이를 그대로 지표에 넣어 등급을 저장하고, `db.save_signal`은 날짜 키로 upsert(`db.py:122-130`)라 하루 중 마지막 값만 남는다.
**손실 시나리오** 11:00 갱신에서 "매수"를 보고 진입 → 15:30 종가 기준으로는 "중립"으로 뒤집힌다. 사용자는 백테스트가 검증한 신호가 아니라 **검증된 적 없는 미완성 봉 신호**로 주문을 냈다. 표본 중첩(ML-7)까지 감안하면 실제 edge(+4% ± 1%p)에서 진입 슬리피지 0.3~0.5%p, 갭 리스크 1%p를 빼면 통계적 우위가 남는지 자체가 불투명해진다.
**수정 방향** (a) 백테스트 진입가를 `open.iloc[i+1]`(익일 시가)로 변경 — 실제로 낼 수 있는 주문. (b) 당일 봉이 확정 전이면 등급 옆에 "미확정" 배지, 또는 확정 봉만으로 시그널을 계산.

### ML-11. 계좌 리스크 지표의 달력 오염 — 변동성이 체계적으로 과소 계상

**증상** 암호화폐(365일 거래)와 주식(약 250일)을 한 프레임에 섞어 계산.
**근거** `backend/app/portfolio.py:133` `frame = pd.DataFrame(series).ffill().dropna()` → 인덱스 합집합. 주말 행에서 주식은 ffill되어 **수익률 0**, 코인만 움직인다. 이후 `portfolio.py:140` `rets = port.pct_change()`, `portfolio.py:162` `rets.std() * (252 ** 0.5)`.
**손실 시나리오** 주식+코인 혼합 계좌에서 (a) 주식 변동성이 약 **17% 과소**(√(252/365) 효과), (b) 코인은 365일 자산인데 √252로 연율화해 약 **20% 과소**, (c) 상관계수는 0 쪽으로 눌려 **분산 효과가 실제보다 커 보인다**. "계좌 변동성 18%"라고 안심하고 레버리지·집중도를 늘렸는데 실제는 22~25%.
추가로 `portfolio.py:127` 주석대로 **현재 수량을 과거 전 구간에 적용**하므로 보고되는 계좌 MDD는 "지금 포지션을 3년 전부터 들고 있었다면"의 값이지 실제 계좌 낙폭이 아니다. 이 사실은 UI에 표기되지 않는다.
**수정 방향** 거래일 **교집합**으로 정렬(또는 주간 리샘플)하고, 연율화 계수를 자산군별로 분리(주식 252, 코인 365). 계좌 MDD에는 "현 포지션 소급 적용" 라벨.

### ML-12. 중장기 등급은 한 번도 검증되지 않았는데 스윙과 동급으로 노출된다

**증상** 백테스트는 `swing_grade`만 집계.
**근거** `backtest.py:35` `rec = {"grade": res["swing_grade"]}` — longterm은 등장하지 않는다. 그런데 `service.py:205-206`이 `longterm_score`/`longterm_grade`를 대시보드 시그널에 실어 보내고, 프론트는 두 등급을 나란히 배지로 보여준다.
게다가 중장기 점수는 스윙의 MACD·RSI를 **그대로 재사용**(`scoring.py:141`)하므로 두 점수는 독립적 관점이 아니다.
구조적 문제도 하나 더 있다 — `scoring.py:85-89`의 `_score_pos_52w`는 52주 고점권(>0.9)을 **−30점 감점**한다. 그런데 `_score_alignment`가 +70을 주는 정배열 상태에서는 pos_52w가 높을 수밖에 없다. 두 항이 서로 상쇄해 중장기 점수의 이론적 최대(0.35·70 + 0.25·50 + 0.20·60 + 0.10·80 + 0.10·80 = **65**)에 도달하는 조합이 존재하지 않는다. 여기에도 `grade()`의 ±60 임계값이 그대로 쓰인다(`service.py:206`).
**손실 시나리오** 사용자가 "중장기 매수"를 근거로 장기 보유를 결정한다. 그 등급이 과거에 어떤 성과를 냈는지 앱은 **모른다**. 검증된 신호와 검증 안 된 신호가 같은 시각적 무게로 놓이면 사용자는 구분하지 못한다.
**수정 방향** 중장기 등급도 별도 horizon(예: 60/120일)으로 백테스트하거나, 검증 전까지 "미검증" 배지를 붙인다. pos_52w의 고점 감점은 모멘텀 문헌과 반대 방향이므로 부호·가중을 재검토.

### ML-13. 지표 중복 — 6지표처럼 보이는 실질 2팩터

**증상** 같은 종가 시계열에서 파생된 과매수/과매도 정보를 세 번 센다.
**근거** `backend/app/scoring.py:3-4`
```python
SWING_WEIGHTS = {"rsi": 0.20, "macd": 0.20, "sma_cross": 0.20,
                 "bollinger": 0.15, "stoch": 0.15, "volume": 0.10}
```
평균회귀군 = rsi 0.20 + bollinger 0.15 + stoch 0.15 = **0.50**. 추세군 = macd 0.20 + sma_cross 0.20 = **0.40**. 거래량만 0.10으로 독립.
RSI(종가 기반), 볼린저 %B(종가 기반), 스토캐스틱(고저·종가 기반)은 동일 국면에서 거의 동시에 극단값을 낸다 → 사실상 하나의 신호에 절반 가중치.
**손실 시나리오** 다양성이 있다고 착각하고 이 점수 하나에 의존한다. 실제로는 "과매도인가 / 추세가 위인가" 두 질문의 가중 평균이며, 그 둘은 `_apply_regime`(`scoring.py:112-124`)에서 다시 한 번 상호작용한다. 6개 중 4개가 동의하니 강한 신호라는 직관이 통계적으로 성립하지 않는다.
**부수 문제** 가중치·임계값(80/40/−80, 60/20/−20 등)의 산출 근거가 코드·문서 어디에도 없다. 과거 데이터에 맞춘 흔적이 없다는 점은 오히려 과최적화 위험을 낮추지만, 동시에 **아무 근거가 없다**는 뜻이기도 하다.
**수정 방향** 평균회귀 3지표를 하나의 합성 팩터(예: 평균 z-score)로 묶고 가중을 재배분. 각 지표의 등급별 단독 성과를 백테스트해 가중치에 근거를 만든다.

## 4. 방법론 개선 제안

### P0 — 이걸 고치기 전에는 이 앱의 숫자로 사이즈를 정하면 안 된다

1. **실현손익에 수수료·세금 반영** (ML-2). *실전 이유:* 복기의 목적은 "내 매매가 비용을 이기는가"를 판정하는 것이다. 비용이 0인 원장은 이 질문에 답할 수 없고, 승률이 좋게 나오는 만큼 회전을 늘리게 만들어 손실을 가속한다.
2. **포지션 사이즈에 노셔널 상한 + 계좌 총 리스크 합산** (ML-4). *실전 이유:* 사이징 오류는 한 번에 계좌를 날린다. 시그널이 틀리는 건 정상이고 사이즈가 틀리는 건 회복 불가다.
3. **환율 완전 정산 — 평균 매수 환율 추적** (ML-3). *실전 이유:* 40%대 오차가 나는 손익으로는 KR/US 배분 판단이 성립하지 않는다.
4. **등급 임계값 실측 재보정** (ML-1). *실전 이유:* 최상위 등급이 0회면 등급 기반 사이징·백테스트 표·대시보드 정렬이 전부 죽은 축을 쓰고 있는 것이다.
5. **백테스트 승률을 비용 차감 후 기준으로** (ML-6). *실전 이유:* 승률은 사용자가 사이즈를 키울 때 쓰는 숫자다. 여기서 부풀리면 위 2번의 사이징 문제와 곱해진다.

### P1 — 숫자를 믿을 수 있게 만드는 작업

6. **백테스트 진입가를 익일 시가로 + 미확정 봉 배지** (ML-9). *실전 이유:* 실제로 낼 수 없는 주문으로 검증한 성과는 성과가 아니다.
7. **백테스트에 2×ATR 손절을 이식** (ML-8). *실전 이유:* 검증한 전략과 실행하는 전략이 같아야 백테스트가 의미를 갖는다.
8. **비중첩 에피소드 수 + 신뢰구간 표기, 표본 하한 게이팅** (ML-7, ML-10). *실전 이유:* "+4%"와 "+4% ± 1%p (독립 표본 202)"는 완전히 다른 의사결정을 낳는다.
9. **손절 감시를 일중 저가 기준으로 + "자동 주문 아님" 명시** (ML-5). *실전 이유:* 사용자는 손절가가 표시되면 그것이 지켜진다고 가정한다. 지켜지지 않는다는 사실 자체가 리스크 정보다.
10. **account_risk 달력 정렬 + 자산군별 연율화 + MDD 라벨** (ML-11). *실전 이유:* 계좌 변동성을 과소 계상하면 "여유 있다"는 잘못된 신호로 집중도를 키운다.
11. **중장기 등급 백테스트 또는 "미검증" 배지** (ML-12). *실전 이유:* 검증 여부가 표시되지 않으면 사용자는 모든 숫자를 동등하게 믿는다.

### P2 — 방법론 정련

12. **평균회귀 3지표를 1개 합성 팩터로, 가중치에 백테스트 근거 부여** (ML-13). *실전 이유:* 실질 팩터 수를 알아야 신호 하나에 얼마를 걸지 판단할 수 있다.
13. **시장별 비용 상수 + 유동성 기반 스프레드 추정** (ML-15).
14. **trades에 체결 시각·수수료 컬럼, 예수금 자동 연동, 초과 매도 입력 거부** (ML-14).
15. **pos_52w 부호·가중 재검토(모멘텀 역행), 종가 대신 고저 기준 범위 사용** (`indicators.py:56-60`, `scoring.py:85-89`).
16. **목표가 산출 추가** — 현재 손절가만 제안하고 목표가는 사용자 수동 입력(`custom_rules`)이다. 손익비를 사전에 계산할 수 없으면 진입 판단의 절반이 비어 있다.

## 5. 신뢰할 만한 부분

1. **백테스트에 룩어헤드가 없다.** `indicators.py`의 모든 계산이 인과적(rolling/ewm)이고, `backtest.py:34`가 `enriched.iloc[:i + 1]`로 시점을 정확히 자른다. 심리지표를 과거 적용에서 제외한 판단(`backtest.py:5` 주석)도 정직하다. 개인 프로젝트에서 이 부분이 맞는 경우는 드물다.
2. **시장 심리로 점수를 보정하지 않는다.** `sentiment.py:76-78`의 주석 — "검증 안 된 선형 보정으로 지표 점수를 왜곡하는 것보다 맥락 표기가 정직하다". 넣고 싶은 유혹을 참은 것이 이 코드베이스에서 가장 트레이더다운 결정이다.
3. **상승장 착시를 스스로 경계한 흔적.** 벤치마크 초과수익(`backtest.py:44-45`), 왕복 비용 차감 표기, 3년 구간 확대(`service.py:12` 주석 "한 국면짜리 400일 검증은 상승장 착시를 못 거른다"), 표본 중첩 주의 문구(`TickerDetail.tsx:196`). 방향은 전부 맞다 — 다만 문구에 그치고 숫자에 반영되지 않은 것이 문제(ML-6, ML-7).

## 6. 미확인 항목

- **실제 체결 내역과 원장의 대조.** 저장소 루트에 `거래내역증명서_*.pdf` 2건과 `보유종목_거래내역.csv`, `mystock_import.sql`이 있으나 대조하지 않았다. 수수료·세금 컬럼이 원본 CSV에는 존재하는지, import 과정에서 버려지는지는 확인 필요.
- **수정주가 일관성.** US는 `auto_adjust=True`(`fetchers.py:40`)로 배당·분할 조정, KR은 FinanceDataReader 기본 동작에 의존(`fetchers.py:35`). 두 소스의 조정 정책이 다르면 KR/US 백테스트 결과가 같은 기준이 아니다. 외부 호출 없이는 확인 불가.
- **장중 부분 봉 실제 동작.** 정적 분석상 KR/US 모두 당일 미완성 봉을 반환할 가능성이 높지만(ML-9), 실제 장중 응답을 받아본 것은 아니다.
- **텔레그램 발송 경로.** `service.py:138-156`은 예외를 조용히 삼킨다(`except Exception: pass`). 실패가 사용자에게 전혀 보이지 않으므로, 알림이 오지 않는 상태를 "조건 미도달"로 오해할 수 있다 — 이건 코드로 확인된 사실이나, 실제 발송 성공률은 미확인.
- **grade_at_trade 스냅샷의 정확성.** `schema.sql:19`에 컬럼은 있으나 매매 입력 시 어떤 시점 등급이 들어가는지(사용자 수동 선택인지 자동 스냅샷인지)는 API 레이어를 더 봐야 한다.
- **프론트 전체 문구.** `Dashboard.tsx`/`Watchlist.tsx`는 이번 리뷰에서 부분만 확인했다. 숫자 의미를 왜곡하는 라벨이 더 있을 수 있다.
